# 문서대로 끝까지 구현

입력은 기획·요구사항 문서 하나다(인자로 받은 경로. 없으면 사용자가 가리킨 문서).
이 문서는 사람이 정할 것과 준비물을 미리 모두 확정해 둔 것이다. 그래서 시작한 뒤에는 사용자에게 묻지 않고 끝까지 간다.

## 1. 시작 전 점검

시작 전 점검은 사용자에게 무언가를 요청할 수 있는 유일한 시점이다. 빠진 것이 있으면 한 번에 모아 알리고 시작하지 않는다.

- 문서 전체와 프로젝트 규칙(CLAUDE.md, 기록 문서 등)을 읽는다. 문서에 없는 것은 프로젝트의 기존 결정을 따른다.
- 문서에 미확정 표시(확정 필요, TODO, 빈 값 등)가 남아 있지 않은지 확인한다.
- 문서의 준비물이 실제로 준비됐는지 확인한다.
  - 환경 변수: 이름이 있고 값이 비어 있지 않은지만 본다. 값을 출력하거나 기록하지 않는다.
  - 외부 계정: 문서에 적힌 수단(CLI, API 키)으로 읽기 요청 하나씩을 보내 접근되는지 본다.
- 이미 진행 기록(3장)이 있으면 처음부터 다시 하지 않고 그 기록에서 이어 간다.

## 2. 원칙

- **모든 요구사항을 만족해야 끝난다.** 요구사항 사이에 우선순위는 없다. 어렵거나 오래 걸린다는 이유로 빼거나 기준을 낮추지 않는다.
- **끝은 "확인"으로 판단한다.** 요구사항마다 문서의 확인 방법을 실제로 실행해 통과해야 만족이다. "구현했으니 될 것이다"는 만족이 아니다.
- **멈추지 않는다.** 설계, 라이브러리, 구조, 화면 세부, 문구처럼 문서가 정하지 않은 것은 스스로 정한다(5장). 막히면 다른 방법을 찾는다.
- **요구사항을 두 가지로 읽을 수 있으면 더 엄격한 쪽**(두 해석을 모두 만족하는 쪽)을 택하고 진행 기록에 남긴다.
- **멈추는 경우는 정해져 있다.** 문서의 멈출 조건과 아래 경우뿐이다.
  - 문서의 사전 승인 밖에 있는 비용, 외부 공개, 되돌릴 수 없는 삭제가 필요할 때
  - 요구사항끼리 충돌해 둘 다 만족할 수 없을 때
  - 준비물(계정, 권한, 키)이 막혀 다른 방법이 없을 때
  - 하면 안 되는 일(비밀번호 입력, 계정 생성, 보안 설정 변경 등)이 필요할 때
- 멈출 조건에 걸려도 **그 부분만 보류**하고, 영향을 받지 않는 나머지는 계속한다. 보류한 것은 진행 기록에 남기고 마지막에 한꺼번에 알린다. 전체가 막힐 때만 그 자리에서 알리고 멈춘다.
- 문서의 범위를 넓히지 않는다. 하고 싶은 개선이 보이면 하지 않고 결과 보고의 "제안"에 적는다.

## 3. 진행 기록

작업은 길고, 중간에 맥락이 요약되거나 세션이 끊길 수 있다. 그래서 진행 상황을 파일로 남긴다.

- 위치: 입력 문서와 같은 폴더에 `<문서 이름>.progress.md`. 입력 문서 자체는 고치지 않는다(문서가 고치라고 한 부분은 예외).
- 내용:
  - 요구사항 체크리스트: 요구사항마다 상태(대기/진행/만족/보류)와 확인 근거(실행한 명령, 테스트 이름, 스크린샷 등)
  - 작업 계획: 스스로 정한 작업 단계와 순서. 계획이 바뀌면 고친다
  - 재량 결정: 정한 것과 이유
  - 보류: 무엇이, 왜, 무엇이 있으면 풀리는지
  - 비용: 문서에 비용 상한이 있으면 지금까지 쓴 비용
- 단계를 마칠 때마다 갱신한다.
- 맥락이 요약된 뒤에는 이 스킬 파일, 입력 문서, 진행 기록, git 기록을 다시 읽고 이어 간다. 요약에는 지침(멈출 조건, 커밋 규칙 등)이 흐려져 남기 때문이다.

### 오래 걸리는 작업

대량 API 호출, 데이터 이전, 배포처럼 오래 걸리는 작업은 끊겨도 비용과 시간을 다시 쓰지 않게 한다.

- 백그라운드로 실행하고, 기다리는 동안 그 작업에 의존하지 않는 일을 한다.
- 다시 실행하면 끝난 부분은 건너뛰고 이어서 하도록(멱등) 만든다.
- 진행 상황(끝난 수, 실패한 수, 다시 시작하는 방법)을 진행 기록에 남긴다.

## 4. 작업 단위와 커밋

- 시작할 때 요구사항 전체를 보고 작업 계획(단계와 순서)을 세운다. 순서는 의존 관계로 정한다. 우선순위로 정하지 않는다.
- 프로젝트의 브랜치 규칙과 문서의 작업 브랜치를 따른다. main 머지는 문서가 허락하지 않으면 하지 않는다.
- **의미 있는 작업 단위마다 커밋한다.** 커밋마다 빌드와 테스트가 통과하는 상태여야 한다. 커밋 메시지는 저장소의 기존 방식을 따른다.
- 문서가 push를 승인했으면 커밋한 단계마다 push한다.
- 비밀 값, 무시해야 할 파일, 문서가 금지한 내용이 커밋에 들어가지 않았는지 커밋 전에 확인한다.

## 5. 재량 결정

- 기존 코드와 프로젝트 결정에 맞는 쪽, 더 단순한 쪽, 되돌리기 쉬운 쪽을 고른다.
- 외부 서비스, 라이브러리, API의 현재 동작은 기억으로 짐작하지 않는다. 공식 문서나 설치된 패키지의 문서·타입을 확인한다.
- 정한 것은 이유와 함께 진행 기록에 남긴다.
- **디자인**: 문서가 가리킨 시안이 있으면 그대로 따른다. 문서에 디자인 기준이 없는 화면은 프로젝트의 기존 디자인(색 토큰, 글꼴, 컴포넌트)을 따라 기존 화면과 같은 모양으로 만들고, 새 스타일을 만들어 내지 않는다.
  새로 만들거나 크게 바꾼 화면은 결과 보고에 스크린샷을 붙인다.

## 6. 서브에이전트 활용

메인 에이전트는 계획, 통합, 판단을 맡는다. 맥락을 많이 먹거나 독립적인 일은 서브에이전트에게 적극적으로 맡긴다.

- **맡기기 좋은 일**
  - 코드베이스 탐색과 조사(외부 문서, 라이브러리 사용법)
  - 서로 다른 파일을 건드리는 독립적인 구현 조각
  - 요구사항별 확인 실행(테스트 작성, 화면 확인)
  - 단계를 마친 뒤의 코드 리뷰
- **동시에 맡기지 않는 일**: 같은 파일을 고치는 작업 여러 개. 병렬로 고쳐야 하면 각자 격리된 작업 공간(worktree)에서 하고, 메인이 합친다.
- 맡길 때는 목적, 건드릴 파일 범위, 완료 기준, 하지 말아야 할 것(범위 밖 수정, 커밋, 외부 행동)을 적는다.
- 결과는 보고만 믿지 않는다. 메인이 diff를 보고 테스트를 돌려 확인한 뒤 커밋한다.
- 요구사항 해석이나 재량 결정은 메인이 한다. 서브에이전트가 판단이 필요하다고 보고하면 메인이 정한다.

## 7. 검증

- 요구사항의 확인은 가능한 한 자동 테스트로 만든다. 자동화할 수 없으면 실제로 실행해 보고(개발 서버와 브라우저, CLI 등) 근거를 남긴다.
- 화면은 프로젝트가 정한 개발 환경에서 확인한다. 운영 환경에서는 기록이 남는 조작을 하지 않는다.
- **마지막 검증**: 모든 요구사항이 만족으로 바뀐 뒤 마지막 커밋 기준으로 처음부터 다시 확인한다.
  - 빌드, 타입 검사, 린트, 전체 테스트를 다시 돌린다.
  - 구현에 참여하지 않은 서브에이전트에게 문서와 구현을 대조하게 한다. 요구사항마다 만족 여부와 근거를 받는다.
  - 여기서 나온 문제는 고치고, 고친 뒤 다시 마지막 검증을 한다.

## 8. 마무리

- 문서가 끝날 때 하라고 한 일(상위 문서 갱신 등)을 한다.
- 결과 보고(사용자에게, 그리고 진행 기록 끝에):
  - 요구사항별 상태와 확인 근거
  - 재량으로 정한 것과 이유
  - 보류한 것과 풀 방법
  - 쓴 비용(해당하면)
  - 사용자가 마지막에 확인할 것(문서의 완료 정의)과 확인 방법
  - 제안(범위 밖이라 하지 않은 개선)
