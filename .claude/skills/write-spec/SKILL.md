# 자율 구현 명세서 작성

입력은 바꾸거나 만들려는 내용이다(인자나 대화로 받는다). 결과는 자율 구현 명세서(줄여서 명세서) 하나다. 정의는 [criteria.md](criteria.md) 맨 앞에 있다. `implement-spec` 스킬이 있으면 그 입력이 된다.

이 스킬은 묻지 않고 진행하는 `implement-spec`·`review-spec`과 반대로, **사용자에게 묻고 결정을 받는 단계**다.
구현이 시작된 뒤에는 물을 수 없으므로, 사람이 정할 것은 모두 여기서 끝낸다.

**기준은 같은 폴더의 [criteria.md](criteria.md)다.** 언제 쓰는지, 원칙, 구성, 빠뜨리기 쉬운 것, 목록 밖을 찾는 점검이 모두 거기 있다. 이 파일은 진행 방법만 다룬다.

## 1. 준비

- `criteria.md`를 읽는다. 구현 스킬이 있으면 그것도 읽는다(진행 규칙에 무엇을 쓰지 않아도 되는지 알기 위해서).
- **명세서가 맞는 일인지 본다**(`criteria.md` 1장). 한 세션에서 대화하며 끝낼 만한 일이면 그렇게 알리고, 명세서 없이 진행할지 사용자에게 묻는다.
- 종류를 정한다. **변경 건**(기존 코드·운영 중인 시스템을 바꾼다)인지 **신규 개발**(새로 만든다)인지에 따라 `criteria.md` 4장에서 대조할 항목이 달라진다. 분명하지 않으면 첫 질문에 넣는다.
- 기존 프로젝트가 있으면 프로젝트 규칙(CLAUDE.md, 기록 문서 등), 개요 문서, 관련 코드를 읽는다.
  신규 개발이면 사용자가 참고하라고 한 자료(비슷한 프로젝트, 기획 메모)를 읽는다.
- 이전에 쓴 명세서가 있으면 예시로 읽는다. 구성과 말투는 따르되, 그 문서에만 해당하는 내용은 가져오지 않는다.
- 문서 위치와 이름은 프로젝트의 관례를 따른다. 관례가 없으면(신규 개발 등) 첫 질문에 넣는다.
- 비공개 데이터와 비밀 값이 어디 있는지 확인한다. 비밀 값은 이름만 본다.

## 2. 뼈대 먼저

- `criteria.md` 3장 구성으로 문서 뼈대를 바로 만든다. 필수 요소와 고정 제목은 빠짐없이 두고, 순서와 묶는 방식은 이 일에 맞게 정한다.
  아는 것은 채우고, 정해야 할 곳에는 `확정 필요: <무엇을>`을 남긴다.
- 사용자가 처음 말한 내용은 목표·범위에 옮긴다. 짐작한 내용은 짐작이라고 표시하고 질문으로 확인한다.
- 범위가 한 문서에 담기에 크면(`criteria.md` 원칙 6) 단계를 어떻게 나눌지 먼저 제안하고, 이 문서는 첫 단계만 다룬다.

## 3. 질문으로 확정하기

- **첫 질문 묶음에 열린 질문을 넣는다**(`criteria.md` 5장 1). "이 일에서 걱정되는 것, 하면 안 되는 것, 이미 아는 함정이 있나요?" 답은 결정·범위·요구사항·진행 규칙 중 맞는 곳에 넣는다.
- `확정 필요`를 중요한 것부터, **한 번에 최대 3개**씩 묻는다. 뒤 질문을 바꾸는 결정(범위, 단계 나누기, 기술 선택, 서비스, 공개 여부)을 먼저 묻는다.
- 질문마다 선택지와 영향(비용, 위험, 되돌리기 쉬운지)을 짧게 적고, 추천안을 앞에 둔다. 외부 서비스의 요금·제한은 기억으로 쓰지 않고 공식 문서로 확인한다.
- 사용자가 정할 필요가 없는 것은 묻지 않고 AI 재량으로 남긴다. 경계는 `criteria.md` 원칙 3을 따른다.
  신규 개발은 따를 기존 방식이 없어서 사용자가 정할 기술 선택이 변경 건보다 많다.
- 답을 받으면 **바로 문서에 적는다.** 날짜, 누가 정했는지, 이유, 뺀 안과 이유(`criteria.md` 원칙 4).
  문서 밖에도 남아야 하는 결정(프로젝트 결정 기록 등)은 프로젝트 규칙에 따라 함께 기록한다.
- 결정이 바뀌면 앞 결정을 지우지 말고 바뀐 것과 이유를 적는다. 앞 결정에 기대 쓴 요구사항도 함께 고친다.

## 4. 요구사항과 확인

- 범위의 "넣는 것"마다 요구사항을 쓰고, 요구사항마다 "확인"을 붙인다(`criteria.md` 원칙 7·8).
- 다 쓰면 `criteria.md` 4장 "빠뜨리기 쉬운 것"의 공통 항목과, 종류에 맞는 항목(기존 시스템을 바꿀 때 / 새로 만들 때)을 하나씩 대조한다. 해당하는데 빠진 것은 요구사항으로 더하거나 질문으로 돌린다.
- 이어서 **구현을 따라가 본다**(`criteria.md` 5장 2). 구현하는 AI가 되었다고 생각하고 시작부터 결과 보고서까지 짚으며, 사람이 필요한 지점을 찾는다. 찾은 것 중 사용자가 정할 것은 질문으로 돌린다.
- 기존 코드·데이터가 있으면 요구사항이 그것과 맞는지 직접 확인한다(읽기 전용). 확인이 실제로 통과할 수 있어야 하기 때문이다.

## 5. 디자인 시안

- 사람이 정해야 할 화면(첫인상, 새 화면의 방향)이 있으면 시안을 2~3개 만들어 고르게 한다.
  기존 디자인(색, 글꼴, 컴포넌트)이 있으면 그것을 바탕으로 한다.
- 신규 개발처럼 기존 디자인이 없으면 디자인 기준(색, 글꼴, 기본 화면)부터 시안으로 고르게 한다(`criteria.md` 원칙 12).
- 고른 시안과 사용자가 지적한 수정 사항을 반영해 확정 파일로 두고, 문서가 그 파일을 가리키게 한다.

## 6. 준비물

- 준비물 목록(계정, 권한, 키, 설치, 확정 값)을 만들고, 내가 할 수 있는 것은 하고 사용자가 할 것은 방법을 안내한다.
  - 계정 생성, 비밀번호 입력, 결제, 영구 삭제처럼 사용자만 할 수 있는 일은 사용자에게 맡긴다.
  - 비밀 값은 사용자가 지정한 파일(예: `.env.local`)에 넣게 하고, 문서와 대화에는 이름만 쓴다.
- 준비가 끝난 것은 읽기 요청 하나로 접근되는지 확인하고, "무엇이 어디에 어떤 상태로 있는지"로 적는다.
- 구현 전에 끝내야 하는 작업(저장소 만들기, 이력 정리, 설정 변경 등)은 끝낸 뒤 "다시 하지 않는다"고 적는다.

## 7. 진행 규칙

- 이 문서에만 해당하는 것만 적는다(`criteria.md` 원칙 11). 사전 승인과 비용 상한, 멈추고 물을 것, 프로젝트 규칙의 예외는 사용자에게 확인받는다.
- 신규 개발처럼 브랜치·커밋·머지 규칙이 아직 없으면 여기서 정한다. 프로젝트 규칙 파일로도 남길지 사용자에게 묻는다.

## 8. 마무리

- 미확정 표시(`확정 필요`, TODO, 빈 값)가 남지 않았는지 검색한다.
- 필수 요소와 고정 제목(`criteria.md` 3장)이 모두 있는지, `criteria.md` 2장 원칙을 지켰는지 대조한다.
- **마지막 점검 질문**(`criteria.md` 5장 3)을 스스로 던지고, 남은 곳이 있으면 목록에 없더라도 고친다.
- 문서가 버전 관리되는 위치에 있으면 프로젝트 규칙대로 커밋한다.
- 사용자에게 알린다: 확정한 결정 요약, 사용자가 아직 할 일(있으면), 다음 단계.
  `review-spec` 스킬이 있으면 다음 단계로 그 검토를 권한다(`/review-spec <문서>`). 검토가 끝나면 `implement-spec`으로 구현한다.
